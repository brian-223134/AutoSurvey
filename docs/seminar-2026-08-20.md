## 0. 한 장 요약

**AutoSurvey(NeurIPS 2024)를 서버에서 end-to-end로 재현하고, 세 가지를 고쳤습니다.**

| | 한 일 | 결과 |
|---|---|---|
| 재현 | 원본 코드가 실행되지 않아 **버그 11종** 수정 | 서베이 **8편** 생성 (본편 5 + 스모크 3) |
| 개선 1 | 논문 DB가 **2024-04에 멈춰** 있었음 → arXiv에서 직접 수집 | 537,665 → **909,293편 (+69%)** |
| 개선 2 | 모델에 따라 분량이 **3배** 벌어짐 → 자유도를 파라미터화 | 계수 실측, 통제 수단 확보 |
| 평가 | LLM judge를 포기하고 **SurveyBench 인용 커버리지**로 전환 | 정량 수치 확보 (**아래 §5**) |

**가장 중요한 발견 두 가지:**

1. **인용을 많이 하는 것이 품질이 아닙니다.** 우리 산출물은 476편을 인용해 벤치마크
   정답을 48편 맞혔습니다. SurveyForge는 85편만 인용해 37편을 맞혔습니다.
   **정답을 더 많이 찾았지만(재현율 0.079 > 0.061), 점수는 4배 낮습니다(0.101 < 0.435).**
2. **분량 문제는 미관 문제가 아니라 점수 문제입니다.** 지표가 정밀도형이라
   분량·인용이 팽창하면 그대로 점수가 깎입니다. §4와 §5가 별개 얘기가 아닙니다.

## 1. 배경 — 왜 이걸 재현하나

**AutoSurvey**는 토픽을 주면 LLM이 arXiv 논문을 검색해 **서베이 논문을 통째로 써 주는**
시스템입니다 (NeurIPS 2024, [arXiv:2406.10252](https://arxiv.org/abs/2406.10252)).

비교 대상으로 **SurveyForge**, **AutoSci**를 함께 보고 있고, 이 발표는 그중
AutoSurvey 쪽 진행분입니다.

**재현이 목적이 아니라 baseline 확보가 목적입니다.** 세 시스템을 같은 조건에서 비교하려면
먼저 각각이 돌아가야 하는데, AutoSurvey는 받은 그대로는 실행되지 않았습니다.

### 파이프라인

```
토픽
 └→ [1] 검색      토픽을 임베딩해 FAISS로 초록 top-K 검색     (--outline_reference_num 1200)
 └→ [2] 아웃라인   그 초록들로 섹션/서브섹션 + 각 설명 생성      (--section_num)
 └→ [3] 본문      서브섹션마다 다시 검색해 병렬 작성            (--rag_num 60, --subsection_len)
 └→ [4] 정제      인접 서브섹션 문맥으로 다듬기 (LCE)
 └→ [5] 참고문헌   인용 번호 → arXiv id 매핑
      → {topic}.md / {topic}.json
```

- 검색은 **초록만** 씁니다. 논문 원문은 공개 DB에 없습니다 (→ §7 한계).
- [3]은 서브섹션마다 스레드를 띄워 병렬로 씁니다. **실행 시간을 지배하는 것은
  토큰량이 아니라 이 동시 요청 수**입니다 (§3 실측).
- 임베딩은 `nomic-ai/nomic-embed-text-v1`. **바꾸면 인덱스 전체가 무효**가 되는데
  에러 없이 엉뚱한 논문이 검색됩니다.

> **말할 것**: "서베이를 쓰는 게 아니라, 검색 → 개요 → 병렬 집필 → 정제의 파이프라인입니다.
> 각 단계가 파라미터를 갖고 있고, 이번에 그 파라미터들이 실제로 통제되는지를 봤습니다."

## 2. 재현 — 원본은 실행되지 않았습니다

**버그 11종**을 고쳤습니다. 그중 셋이 결정적이었습니다.

| 패치 | 없으면 |
|---|---|
| 죽은 `langchain.document_loaders` import 제거 | `ImportError`로 **즉사** |
| `[[]] * n` aliasing 버그 (`src/agents/writer.py`) | **크래시 없이** 섹션 0을 뺀 전 섹션이 섹션 0의 참고문헌으로 본문을 씀 |
| TinyDB 선형 스캔 → dict 인덱스 (`src/database.py`) | 호출당 수 분 정지 |

> **가운데 것이 제일 위험합니다.** `[[]] * n`은 같은 리스트 객체를 n번 참조합니다.
> 파이썬을 좀 아는 사람도 지나치는 버그이고, **에러가 안 납니다.**
> 결과물은 그럴듯하게 나오는데 섹션 2~8이 전부 섹션 1의 논문으로 쓰여 있습니다.
> 산출물만 보고는 알 수 없어서, **재현이란 "돌았다"가 아니라 "맞게 돌았다"**를
> 확인하는 일이라는 걸 이 버그에서 배웠습니다.

**기능 추가 5종**은 전부 **기본값이 원본 동작**입니다. 환경변수·인자를 주지 않으면
원본과 글자 단위로 같은 프롬프트가 나갑니다.

| 변경 | 내용 |
|---|---|
| `src/prompt.py` | `several subsections` → `[SUBSECTION NUM] subsections` (값 없으면 `several`) |
| `src/agents/outline_writer.py` | 초과 서브섹션 코드 레벨 절단 |
| `src/model.py` | **provider 고정** — 안 하면 서브섹션마다 다른 quantization이 씀 |
| `src/model.py` | **출력 잘림 검사** — 원본은 잘린 응답을 그대로 반환 |
| `main.py` | 모델·provider 정합 검사 (DB 로딩 전 중단) |

**프롬프트의 "내용"은 바꾸지 않았습니다.** 문구를 다시 쓰면 원본 AutoSurvey가 아닌
다른 시스템이 되어 baseline으로서의 의미가 사라집니다. placeholder만 넣었습니다.
이 원칙은 `tests/` **66개**가 회귀 테스트로 지킵니다 (0.2초, 네트워크·GPU 불필요).

> **말할 것**: "고친 것과 바꾼 것을 분리했습니다. 버그는 고쳤고, 프롬프트 문구는
> 손대지 않았습니다. 비교 대상이 되려면 원본이어야 하니까요."

## 4. 개선 — 두 가지

### 4.1 DB 최신화 (완료)

**DB에 수록된 논문의 최신 날짜가 2024-04-26이었습니다.** 현재 기준 **27개월** 공백입니다.
서베이 생성기로서는 치명적입니다 — 그 사이 부상한 주제는 검색 자체가 안 됩니다.

arXiv OAI-PMH로 전체 CS를 직접 수집했습니다. **LLM API를 전혀 쓰지 않아** 크레딧이
소진된 상태에서 진행할 수 있었습니다.

| 실측 | 값 |
|---|---|
| 수집 | 419,246건 / 646요청 / **2시간** (재시도·503 **0건**) |
| 추가 | **371,628편** (cutoff 이후 350,805 + 배포본 결손분 20,823) |
| 임베딩 + 인덱스 병합 | **30분** (L40S 1장) |
| 결과 | **537,665 → 909,293편 (+69%)** |

사전에 `ListIdentifiers`로 센 419,246건과 실제 수집량이 **정확히 일치**했습니다.

**검색 품질 개선도 쟀습니다** (`d@1200` = top-1200 평균 거리, 낮을수록 좋음):

| 토픽 | 배포본 → 최신화본 | top-1200 교집합 |
|---|---|---|
| In-context Learning | 0.853 → **0.796** | 34.9% |
| Evaluation of LLMs | 0.849 → **0.764** | 16.2% |
| Large Multi-Modal LM | 0.744 → **0.691** | 25.5% |

> **교집합이 16~35%뿐이라는 건 검색 결과가 대부분 바뀌었다는 뜻입니다.**
> 그래서 **기존 8편과 최신화 DB 산출물은 통제 비교가 성립하지 않습니다.**
> 두 스냅샷을 모두 보존한 이유입니다. 벤치마크 채점은 배포본으로, 최신화 효과 시연은
> 최신화본으로 나눠 돌려야 합니다.

### 4.2 분량 통제 (부분 성공)

같은 `--subsection_len 700`인데 모델에 따라 분량이 **3배** 벌어집니다.

| 산출물 | 서브당 단어 | **지시값 대비** |
|---|---|---|
| haiku × 3편 | 531~537 | **0.76×** (미달) |
| deepseek-v4-pro | 1,167 | **1.67×** |
| v4-flash | 1,211~1,256 | **1.76×** |

**원인은 프롬프트입니다.** `"content more than [WORD NUM] words"` — **하한만 있고
상한이 없습니다.** 지시를 잘 따르는 모델일수록 넘겨 쓰고, 약한 모델은 미달합니다.
`max_tokens`는 코드 어디에도 없습니다.

**대응: 프롬프트 문구는 그대로 두고 파라미터화 + 캘리브레이션.**
목표 분량을 모델 계수로 나눠 `--subsection_len`에 넣습니다.

**결과는 절반의 성공입니다.**

| 자유도 | 통제 |
|---|---|
| `--subsection_num` | ✅ 지켜짐 — 10개 섹션 전부 4개 이하 |
| `--section_num` | ❌ **두 실행 모두 정확히 1.25배 초과** (4→5, 8→10) |

섹션이 8→10으로 늘어 서브섹션 상한을 상쇄했습니다. 그래서 개수를 묶었는데도
총 서브섹션이 37→39로 **오히려 늘었고**, 예측 35,000단어에 49,002가 나왔습니다.
예측식에 섹션 초과를 반영했습니다:

```
총 분량 = (section_num × 1.25) × subsection_num × (subsection_len × 1.76)
검산: 8 × 1.25 × 3.9 × 1,232 = 48,000 ≈ 실측 49,002
```

**부수적으로 확인한 것 — `--rag_num`은 분량 인자가 아니라 비용 인자입니다.**
서브섹션당 논문을 15 → 60편으로 **4배** 늘렸는데 서브섹션당 단어는 1,211 → 1,256으로
**4% 늘었을 뿐**입니다. 대신 비용은 2.3배가 됐습니다.

> **말할 것**: "분량을 통제하려고 두 손잡이를 잡았는데 하나만 잡혔습니다.
> 섹션 수가 25% 새는 걸 이번에 처음 확인했고, 예측식에 넣었습니다."

## 5. 평가 — 무엇을 쟀고, 무엇을 못 쟀나

> **이 절이 이번 발표의 핵심입니다.** 상세는 [`evaluation-note.md`](evaluation-note.md).

### 5.1 LLM-as-Judge는 포기했습니다

원본의 `evaluation.py` / `judge.py` 경로를 쓰지 않기로 **확정**했습니다. 이유는 셋입니다.

1. **코드가 죽어 있습니다.** `src/utils.py::compute_price()`가 `KeyError`로 즉사합니다
   (`self.model_price = {}`가 비어 있는데 조회). `judge.py:46`이 호출하므로 **어떤 모델을
   써도 터집니다.** `main.py`는 이 경로를 타지 않아 드러나지 않았을 뿐입니다.
2. **인용 문장 하나당 스레드 하나**를 무제한 생성합니다 (`judge.py:202,216`).
3. **LLM judge는 자기 자신을 평가하는 구조**라 점수의 신뢰도가 낮고, 비용도 듭니다.

### 5.2 대신 SurveyBench 인용 커버리지를 씁니다

SurveyForge 저자들이 공개한 벤치마크에 **10개 토픽의 정답 참고문헌**(`ref_bench`),
**인간이 쓴 서베이**, **SurveyForge 산출물**이 들어 있습니다.

```
coverage = |생성 참고문헌 ∩ ref_bench| / |날짜 필터를 통과한 생성 참고문헌|
```

**arXiv id 집합의 교집합이라 LLM 호출이 0회입니다.** 크레딧이 필요 없고, 재현됩니다.
채점 함수는 SurveyBench의 `test.py::compute_citation_coverage`를 **그대로 import**해서
씁니다 — 다시 구현하면 그쪽이 바뀔 때 조용히 어긋나 비교가 무의미해집니다.

### 5.3 실측 결과 (2026-08-18, 토픽: RAG for LLMs / 벤치마크 정답 608편)

|---|---|---|---|---|
| 인간 작성 서베이 | 191 | 103 | **0.539** | **0.169** |
| SurveyForge (저자) | 85 | 37 | **0.435** | 0.061 |
| **우리 본편 (rag 60)** | **476** | **48** | **0.101** | **0.079** |
| 우리 스모크 (rag 15) | 268 | 22 | 0.082 | 0.036 |

(다르면 검색 쿼리부터 달라져 비교가 성립하지 않습니다).</sub>

**읽는 법이 중요합니다.**

- **coverage는 사실상 정밀도입니다.** 분모가 "우리가 인용한 편수"라
  **많이 인용할수록 기계적으로 낮아집니다.**
- **재현율로 보면 우리가 SurveyForge보다 높습니다** (0.079 vs 0.061).
  정답 608편 중 우리는 48편, SurveyForge는 37편을 찾았습니다.
- 즉 **"못 찾은" 게 아니라 "너무 많이 데려온" 것**입니다. 476편을 인용해 48편이 맞았으니
  **나머지 428편이 벤치마크 기준으로는 군더더기**입니다.

**이것이 §4.2의 분량 문제와 같은 문제입니다.** 분량 통제는 미관 문제가 아니라
**점수에 직결되는 문제**입니다. 발표에서 이 연결을 반드시 짚어야 합니다.

### 5.4 못 잰 것 — 정직하게

| 못 잰 것 | 이유 |
|---|---|
| **내용 품질** (정확성·논리·서술) | 정량 지표가 없습니다. LLM judge를 버렸고 사람 평가는 안 했습니다 |
| **10개 토픽 중 1개만 채점** | `ref_bench`가 10개 토픽에만 있고, 그중 우리가 정확한 문자열로 생성한 건 RAG 1편뿐 |
| **haiku 3편의 커버리지** | 토픽 문자열이 벤치마크와 달라(`"Evaluation of LLMs"` vs `"Evaluation of Large Language Models"`) 검색 쿼리부터 다릅니다. 비교 불가 |
| **DB 최신화의 품질 효과** | 채점기가 `ref_bench` 최신 논문(2024-07)보다 새 인용을 분모에서 뺍니다. 최신화본으로 돌리면 표본이 무너집니다 |
| **논문의 정량 수치 재현** | 논문은 각 논문 **본문 앞 1,500토큰**을 쓰는데 공개 DB에는 초록만 있습니다. 입력이 근본적으로 다릅니다 |

> **말할 것**: "정량 수치는 하나의 토픽, 하나의 지표뿐입니다. 그 지표가 정밀도형이라
> 우리 점수가 낮게 나오는데, 재현율로 보면 SurveyForge보다 높습니다.
> 지표를 하나만 보면 결론이 뒤집힙니다."

### 6.2 문제가 있는 것

| 문제 | 실측 | 기준 |
|---|---|---|
| **참고문헌 과다** | **476편** | 인간 RAG 서베이 **191편**, 우리 가드 400편 |
| **분량 과다** | 49,002단어 = **실측 111페이지** | 표준 구간 12,000~25,000 (26~55p) |
| **참고문헌 주제 이탈** | 제목에 검색/RAG 관련어가 있는 것이 **28%** (134/476) | — |
| **`--section_num` 미준수** | 8 지시 → 10 생성 | — |

**주제 이탈이 가장 아픕니다.** 이탈한 참고문헌은 무작위가 아니라
**"hallucination"에 몰려 있습니다**:

```
Puzzle Solving using Reasoning of Large Language Models: A Survey
Hallucination is Inevitable: An Innate Limitation of Large Language Models
Large Legal Fictions: Profiling Legal Hallucinations in Large Language Models
Deficiency of Large Language Models in Finance: ... Hallucination ...
```

임베딩 검색이 **RAG → hallucination(인접 주제)으로 흘렀습니다.** RAG가 환각 완화
기법이니 의미적으로는 가깝지만, RAG 서베이의 참고문헌은 아닙니다.
**이것이 coverage 0.101의 실질적 원인입니다.**

> **말할 것**: "형식은 완성됐고 내용은 아직입니다. 인용이 안 깨지고 목차가 그럴듯한 것과,
> 참고문헌의 72%가 주제에서 벗어난 것은 별개 문제입니다."

## 7. 한계와 다음 단계

### 알려진 한계

1. **초록만 씁니다.** 논문은 본문 앞 1,500토큰을 쓰는데 공개 DB에는 초록만 있습니다.
   **논문의 정량 수치와는 비교할 수 없습니다.**
2. **통제된 비교는 haiku 3편끼리만** 성립합니다. 나머지는 모델·`rag_num`·DB 스냅샷이
   겹치지 않습니다.
3. **정량 평가가 1개 토픽 × 1개 지표**입니다.

### 다음에 할 것 (우선순위)

| # | 할 일 | 왜 |
|---|---|---|
| 1 | **`--section_num` 초과를 코드로 절단** | 25% 새는 걸 확인했고 `subsection_num`과 같은 방식으로 막을 수 있습니다 |
| 2 | **`rag_num`을 낮춰 재생성 후 재채점** | 인용 팽창이 coverage를 깎는다는 가설의 직접 검증. `rag_num` 15 → 60에서 재현율은 올랐지만(0.036→0.079) 정밀도는 그대로였음 |
| 3 | **`ref_bench` 보유 토픽 2~3개 추가 생성** | 표본 1개로는 결론을 못 냅니다. 편당 $0.38 / 10분 |
