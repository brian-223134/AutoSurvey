# 평가 노트 — 무엇을 어떻게 쟀고, 무엇을 못 쟀나

> 발표에서 가장 방어가 필요한 부분입니다. **"벤치마크 구현이 완벽하지 않다"는 말이
> 구체적으로 무엇을 뜻하는지**를 먼저 정리하고, 그 제약 안에서 무엇을 쟀는지 씁니다.

---

## 1. 평가 수단이 왜 이것 하나뿐인가

서베이 생성기를 평가하는 길은 원래 둘입니다.

| 축 | 무엇을 보나 | 우리 상태 |
|---|---|---|
| **인용 (citation)** | 인용한 논문이 그 주제의 정답 논문인가 | ✅ **가능** |
| **내용 (content)** | 서술이 정확·논리적·포괄적인가 | ❌ **불가** |

두 번째 축이 막혀 있습니다. 이유가 두 개 겹쳤습니다.

### 1.1 AutoSurvey 원본의 LLM judge는 죽어 있습니다

`evaluation.py` / `src/agents/judge.py` 경로를 **쓰지 않기로 확정**했습니다 (2026-08-05).

1. **`src/utils.py::compute_price()`가 `KeyError`로 즉사합니다.**
   `self.model_price = {}`가 비어 있는데 `self.model_price[model][0]`을 조회합니다.
   `judge.py:46`이 이걸 호출하므로 **어떤 모델을 쓰든 터집니다.**
   `main.py`(생성 경로)는 여길 타지 않아 그동안 드러나지 않았습니다.
2. **`judge.py:202,216`이 인용 문장 하나당 스레드 하나**를 무제한 생성합니다.
3. 고친다 해도 **LLM이 LLM의 산출물을 채점**하는 구조라 점수의 신뢰도가 낮고,
   토픽당 수천 회 호출이라 비용이 큽니다.

### 1.2 공개 SurveyBench도 인용만 채점합니다

비교 기준으로 쓰는 `../SurveyForge/SurveyBench/test.py`를 직접 확인했습니다.
**`compute_citation_coverage` 하나뿐입니다.** 내용 품질을 채점하는 코드는
공개본에 없습니다.

> **그래서 "벤치마크 구현이 완벽하지 않다"는 것은 우리 구현이 부실하다는 뜻이 아니라,
> 공개된 정량 평가 자체가 인용 축 하나뿐이라는 뜻입니다.**
> 내용 품질은 현재 **누구도 재현 가능한 방식으로 재고 있지 않습니다.**

## 2. 쓰는 지표의 정확한 정의

`SurveyBench/test.py:50`을 그대로 옮기면:

```
1) 생성 참고문헌과 벤치마크 정답을 모두 arXiv id 로 정규화 (v2, v3 접미사 제거)
2) id 에서 날짜를 파싱 — 실패하면 버림          ← 구형 id(cs/0701001)가 여기서 빠짐
3) 벤치마크 정답 중 가장 최신 논문의 날짜를 구함  ← RAG 토픽은 2024-07
4) 그보다 새로운 생성 참고문헌을 분모에서 뺌      ← 벤치마크가 알 수 없는 논문이라
5) coverage = |남은 생성 참고문헌 ∩ 정답| / |남은 생성 참고문헌|
```

**핵심: 분모가 "우리가 인용한 편수"입니다. 이것은 재현율이 아니라 정밀도입니다.**
많이 인용할수록 기계적으로 내려갑니다.

우리는 이 함수를 **다시 구현하지 않고 그대로 `import` 해서 씁니다.**
같은 식을 옮겨 적으면 그쪽이 바뀔 때 조용히 어긋나고, 그러면 SurveyForge와의 비교가
무의미해집니다 (`scripts/to_surveybench_ref.py`).

### 채점 실행

```bash
python scripts/to_surveybench_ref.py \
  "output/deepseek-v4-flash/Retrieval-Augmented Generation for Large Language Models.json" \
  --topic "Retrieval-Augmented Generation for Large Language Models"
```

**LLM 호출 0회.** 크레딧이 필요 없고 몇 초 만에 끝납니다.
공식 러너(`SurveyBench/test.py`)로 직접 돌려도 같은 값이 나옵니다.

## 3. 실측 결과 (2026-08-18)

**토픽**: `Retrieval-Augmented Generation for Large Language Models`
**벤치마크 정답**: 608편 (최신 2024-07)
**DB**: 배포본 (날짜 필터 때문에 최신화본을 쓰면 표본이 무너집니다 — §5)

| 산출물 | 인용 | 적중 | **coverage (정밀도)** | **재현율** |
|---|---|---|---|---|
| 인간 작성 서베이 | 191 | 103 | **0.539** | **0.169** |
| SurveyForge (저자 산출물) | 85 | 37 | **0.435** | 0.061 |
| **우리 본편 (`rag_num` 60)** | **476** | **48** | **0.101** | **0.079** |
| 우리 스모크 (`rag_num` 15) | 268 | 22 | 0.082 | 0.036 |

<sub>coverage는 `to_surveybench_ref.py` 출력. 재현율(= 적중 / 608)은 지표의 성질을
드러내려고 이번에 추가로 계산한 것으로, 벤치마크의 공식 지표가 아닙니다.</sub>

### 3.1 그대로 읽으면 — 우리가 4배 나쁩니다

0.101 vs 0.435. 숨길 필요 없는 사실입니다.

### 3.2 한 겹 들어가면 — 결론이 뒤집힙니다

**정답 608편 중 우리는 48편을 찾았고 SurveyForge는 37편을 찾았습니다.**
찾은 양은 우리가 **30% 더 많습니다.** 점수가 낮은 이유는 못 찾아서가 아니라
**476편을 인용했기 때문**입니다 (SurveyForge 85편).

```
우리:        476편 인용 →  48편 적중  →  428편이 군더더기
SurveyForge:  85편 인용 →  37편 적중  →   48편이 군더더기
인간:        191편 인용 → 103편 적중  →   88편이 군더더기
```

**인간 서베이가 두 축 모두에서 이깁니다** (정밀도 0.539, 재현율 0.169).
사람은 적게 인용하면서 더 많이 맞힙니다. 이게 진짜 격차입니다.

### 3.3 이것은 분량 문제와 같은 문제입니다

`rag_num`을 15 → 60으로 올렸을 때:

| | 재현율 | 정밀도 |
|---|---|---|
| `rag_num` 15 | 0.036 | 0.082 |
| `rag_num` 60 | **0.079** (2.2배) | 0.101 (1.2배) |

**검색을 늘리면 정답을 더 찾긴 합니다.** 다만 군더더기가 같이 늘어 정밀도는 거의
제자리입니다. 그래서 다음 실험은 **"찾은 뒤 걸러내기"** — 검색량은 유지하고
인용 수를 줄이는 것입니다.

## 4. 품질의 정성 신호 — 참고문헌이 주제에서 벗어납니다

정량 지표가 하나뿐이라, 보조로 **참고문헌 제목의 주제 적합도**를 쟀습니다.

**476편 중 제목에 검색/RAG 관련어가 들어 있는 것은 134편, 28%입니다.**

<sub>`retriev|rag|augment|knowledge base/graph|passage|corpus|index` 정규식.
거친 측정이라 상한이 아니라 하한으로 읽어야 합니다 — 관련어 없는 RAG 논문도 있습니다.</sub>

**이탈이 무작위가 아닙니다. "hallucination"에 몰려 있습니다:**

```
Puzzle Solving using Reasoning of Large Language Models: A Survey
Hallucination is Inevitable: An Innate Limitation of Large Language Models
Why LLMs Hallucinate, and How to Get (Evidential) Closure
Large Legal Fictions: Profiling Legal Hallucinations in Large Language Models
Towards Mitigating Hallucination in Large Language Models via Self-Reflection
Deficiency of Large Language Models in Finance: ... Hallucination ...
```

**임베딩 검색이 RAG → hallucination 으로 흘렀습니다.** RAG가 환각 완화 기법이니
의미적으로는 가깝습니다. 하지만 RAG 서베이의 참고문헌은 아닙니다.
(SurveyBench에 `Hallucination in Large Language Models`가 **별도 토픽**으로 있습니다.)

**coverage 0.101의 실질적 원인이 이것입니다.** 지표가 낮은 게 아니라
검색이 인접 주제로 새고 있고, 지표가 그걸 정확히 잡아낸 것입니다.

## 5. 못 잰 것과, 재려면 필요한 것

| 못 잰 것 | 막힌 이유 | 열려면 |
|---|---|---|
| **내용 품질** | 재현 가능한 공개 채점기가 없음 (§1) | 사람 평가 프로토콜을 직접 설계하거나, judge를 쓰되 한계를 명시 |
| **토픽 일반화** | `ref_bench`가 10개 토픽에만 있고 그중 정확한 문자열로 생성한 건 **RAG 1편** | 편당 $0.38 / 10분. **2~3편 더 생성**하면 해결 |
| **haiku 3편의 커버리지** | 토픽 문자열이 벤치마크와 다름 (`"Evaluation of LLMs"` ≠ `"Evaluation of Large Language Models"`) — 검색 쿼리부터 달라 비교 불가 | 정확한 문자열로 재생성 |
| **DB 최신화의 품질 효과** | 채점기가 **정답 최신 논문(2024-07)보다 새 인용을 분모에서 제외**. 최신화본(2026-08)으로 돌리면 신규 인용이 대량 탈락 | 최신화 효과는 **검색 지표**(`compare_snapshots.py`의 `d@1200`)로 따로 보고, 벤치마크 채점은 배포본으로 |
| **논문 수치 재현** | 논문은 본문 앞 1,500토큰, 공개 DB는 **초록만** | 재현 불가 — 입력이 다릅니다 |

### 이번에 확인한 채점기의 함정 두 개

1. **토픽 문자열은 글자 단위로 같아야 합니다.** 과거 haiku 산출물이 0.054로 나온 적이
   있는데, `"Evaluation of LLMs"`로 생성해 벤치마크의
   `"Evaluation of Large Language Models"`와 달랐던 게 원인입니다.
   생성 시점의 검색 쿼리부터 다르므로 **점수를 비교하면 안 됩니다.**
   (이번 RAG 산출물은 벤치마크 문자열 그대로 생성해 이 문제가 없습니다.)
2. **분모에서 조용히 빠지는 인용이 있습니다.** 구형 arXiv id와 정답보다 새 논문입니다.
   모르면 낮은 점수를 품질 문제로 오독합니다. `to_surveybench_ref.py`가
   **제외 편수를 함께 출력**하도록 만들어 뒀습니다 (이번 실행은 제외 0편).

## 6. 한 문단 요약 (발표용)

> 평가는 인용 축 하나만 가능합니다. AutoSurvey 원본의 LLM judge는 코드가 죽어 있고,
> 공개 SurveyBench도 인용 커버리지만 채점하기 때문입니다.
> 그 하나를 쟀더니 우리 산출물은 0.101로 SurveyForge(0.435), 인간(0.539)보다 낮습니다.
> 다만 이 지표는 정밀도형이라 인용을 많이 할수록 내려갑니다.
> **재현율로 보면 우리가 SurveyForge보다 높습니다(0.079 vs 0.061).**
> 문제는 정답을 못 찾는 게 아니라 476편을 인용해 428편이 군더더기라는 것이고,
> 그 군더더기는 무작위가 아니라 **인접 주제(hallucination)로 새어 나간 검색 결과**입니다.
> 그래서 다음 작업은 인용 수를 줄이는 것과, 표본을 1개 토픽에서 3개로 늘리는 것입니다.
